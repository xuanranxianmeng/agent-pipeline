# 多模型协作任务编排 · 流程规范集

一个大脑负责调度，多个模型各自认领任务区块并行干活。

这套东西不是框架，是**一套能照着执行的流程规范**——把「把一个模糊需求交给 AI 做完」这件事，拆成可交接、可监督、可验收的五个阶段。

```
任务书 → 派发 → 监督 → 验收 → 收尾
  │        │       │       │       │
  │        │       │       │       └─ 结果归档 + 经验回写（下次不再踩同一个坑）
  │        │       │       └───────── 对照任务书逐条核，不合格打回重做
  │        │       └───────────────── 中途检查产出，边做边存，别等最后
  │        └───────────────────────── 按任务类型配模型（见下）
  └────────────────────────────────── 把需求写成可验收的书面形式
```

## 任务书要写清什么

一份能直接发出去的任务书，至少包含六块。**缺任何一块，执行方都会开始猜**，猜错就是返工：

| 块 | 作用 |
|---|---|
| 甲方与验收方 | 谁派、谁验，责任到人 |
| 任务边界 | 只做这一件事，明确不做什么 |
| 环境说明 | 登录态、依赖路径、可用资源 |
| 输出格式 | 字段名、落盘位置、文件结构 |
| 约束 | 不能碰的东西、语言要求、风格要求 |
| 异常处理 | 遇到 429/超时/登录墙怎么办，重试几次，不行怎么降级 |

**关键设计：边做边存。** 任务书里明确要求"中途遇到困难，把已完成的先落盘再继续"——长任务最怕跑完 80% 崩了全丢。

## 任务-模型匹配策略

实测下来，不是所有任务都该丢给最强的模型：

| 任务类型 | 配什么模型 | 理由 |
|---|---|---|
| 批量重复活（格式转换、逐条抄录） | 响应快的轻量模型 | 慢模型做这种活是浪费，量大时成本差一个量级 |
| 复杂推理（方案设计、多步决策） | 深度推理模型 | 快模型在这类任务上返工率明显更高 |
| 中间地带 | 主模型 + 备用降级 | 主模型超时自动切换，任务不中断 |

## 收尾为什么单列一个阶段

大多数自动化流程跑到"产出结果"就停了，问题出在这：

- 结果散落在临时目录，下次找不着
- 这次踩的坑没有记录，下次原样再踩一遍
- 没人定义什么叫"做完了"，于是永远差一点

`收尾规范` 针对这三点，把收尾做成固定动作：**归档 → 自报家门（做了什么、结果如何、有什么问题）→ 经验回写**。

---

## 适用场景

- 把一个大任务拆给多个模型并行做
- 需要把任务交接给「不知道前因后果」的执行方（人或 AI）
- 跑长任务，中途可能失败、需要断点续做
